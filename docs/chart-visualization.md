# 에이전트 응답 차트 시각화

**상태: v1 구현 완료(bar/line). v2는 아래 방향으로 설계 개정, 구현 착수 전.**

[Result Store](result-store.md)의 SQL·표형 시뮬레이션 결과 저장과
[Knowledge 집계 가이드](aggregation-guide.md)는 구현되어 있다.
시각화 tool, 검증된 명세 저장, 시각화 조회 API, 최종 답변 마커 렌더링은 아직 미구현이다.

v2의 기본 흐름은 다음과 같다.

```text
Knowledge 확인
  → 집계 SQL 생성·DB 실행
  → 집계 결과를 parquet에 저장(result_id)
  → LLM이 prepare_visualization 호출
  → 서버 검증·시각화 명세 등록(visualization_id)
  → LLM이 최종 답변에 시각화 참조 삽입
  → 프론트가 명세·데이터를 조회해 차트 렌더링
```

## 1. v1 — 현재 구현과 전환 범위

2026-09-15에 bar/line 차트를 구현했다.

| 구성 요소 | 파일 | 역할 |
| --- | --- | --- |
| 추론 | `backend/services/chart_inference.py` | `infer_chart(columns, rows)` — 결정론적 규칙으로 스펙 조립 |
| 백엔드 연결 | `backend/services/mock/mock_sql_service.py`, `mock_simulation_service.py` | 결과에 선택적 `chart` 필드 첨부 |
| 타입 | `frontend/src/types/chat.ts` | 데이터가 포함된 렌더링용 `ChartSpec` |
| 렌더 | `tool-results/chart-block.tsx`, `charts/*` | Recharts와 로컬 shadcn chart 래퍼 |
| 색상 | `frontend/src/app/globals.css` | `--chart-1` ~ `--chart-5` |

v1은 서비스가 결과 컬럼·행만 보고 차트를 만들고 도구 호출 카드 안에 표시한다.
숫자 컬럼이 정확히 하나일 때만 추론하며, 사용자 질문의 비교·추이 의도를 직접 반영하지 못한다.
최종 답변 본문에는 차트가 없다.

현재 코드·명 쌍은 명 컬럼을 우선한다. 단순 막대는 값 내림차순 상위 20개,
단순 선 차트는 입력 순서의 앞 20행만 표시한다. 그룹 선 차트는 별도 경로이며,
같은 날짜·그룹의 중복 행은 마지막 값으로 덮어쓴다. 이 동작을 v2에 그대로 옮기지 않는다.

### v2에서 재사용·정리할 것

- Recharts, 팔레트, 렌더 컴포넌트와 `ChartSpec`의 뼈대를 재사용한다.
  다중 시리즈 범례·축 라벨·단위·오류 표시는 v2 계약에 맞춰 보완한다.
- `ChartBlock`은 렌더링용 props를 받는 컴포넌트로 유지하고,
  데이터 조회·로딩·오류 관리는 별도 컨테이너가 맡는다.
- v2 전환 완료 전까지 기존 도구 카드 차트와 `infer_chart` 경로를 유지한다.
  전환 시 서비스의 자동 `chart` 첨부와 도구 카드의 중복 차트를 제거한다.
- `infer_chart`는 v2의 자동 폴백으로 사용하지 않는다.
  전환 후 남은 사용처를 확인해 정리하며, 재사용할 데이터 처리도 새 검증 기준을 따른다.

## 2. 집계는 SQL에서, 값은 Result Store에서

### 집계 데이터 준비

LLM은 SQL 작성 전에 `catalog + kpi + recipes`를 조회한다.
집계 단위·필터·조인·비율 계산을 SQL에 반영하고, DB가 계산한 결과를 parquet에 저장한다.
이미 집계가 끝난 결과라면 그대로 저장해 사용한다.

예를 들어 라인별 비교는 라인별 계획·실적 합계, 월별 추이는 연월·라인별 합계를 조회한다.
같은 집계 결과로 표와 차트를 함께 만들 수 있으며, 집계 단위가 달라지면 별도 SQL 결과가 필요하다.
상세 표도 필요하다면 상세 결과와 집계 결과를 각각 저장한다.

차트 서버는 parquet을 읽어 컬럼을 선택하고 정렬·시리즈 분리를 수행한다.
수량을 다시 합산하거나 달성률을 재계산하지 않는다. 추가 집계가 필요하면 LLM에 재조회를 요청한다.
업무 계산 기준은 [aggregation-guide.md](aggregation-guide.md)를 따른다.

### 현재 데이터 계약과 v2 보완

- 현재 SQL 결과는 100행 이하이면 전체 행을, 초과하면 샘플·요약을 LLM에 반환한다.
  따라서 “LLM은 숫자를 보지 못한다”는 전제를 두지 않는다.
- 시각화 tool은 `result_id`와 표현 명세를 입력받고 데이터 값 배열은 받지 않는다.
  차트에 쓰는 실제 수치는 서버가 저장소에서 읽는다.
- 현재 컬럼 dtype·role은 소량 결과 응답에 항상 포함되지 않는다.
  v2에서는 SQL·표형 시뮬레이션 결과의 크기와 관계없이 컬럼 메타데이터를 제공한다.
- 레시피의 `output_grain`·`output_columns`는 CTE 출력에 대한 가이드다.
  외부 SELECT의 별칭·재집계를 거친 최종 결과에 자동으로 전파되지는 않는다.
- 현재 SQL 서비스는 최종 결과도 최대 500행까지만 저장한다.
  원본을 잘라 집계하지 않도록 하고, v2에서는 조회 결과의 잘림 여부를 보존·전달한다.
  저장된 전체 행을 읽는 것과 원래 조회 대상 전체를 읽는 것을 구분한다.

이 구조는 차트 값의 전사 오류를 방지한다. SQL·업무 정의·차트 선택의 정확성은 별도로 검증해야 한다.

## 3. 차트 스펙 결정 — 집계 가이드 기반 제안과 검증

Knowledge, LLM, 서버는 서로 다른 책임을 맡는다.
기존 설계의 “Knowledge → LLM → 규칙” 3단 폴백과 테이블별 `charts:` 자동 매칭은 채택하지 않는다.

| 담당 | 책임 |
| --- | --- |
| Knowledge | 집계 기준·컬럼 의미·권장 표현 제공 |
| LLM | 질문 해석, SQL 생성, 실행 결과에 맞는 차트 종류와 컬럼 연결 제안 |
| 서버 | 실제 데이터로 명세 검증, 시각화 등록, 렌더링용 스펙 구성 |
| 프론트 | 등록된 명세와 데이터를 준비된 컴포넌트로 렌더링 |

사용자의 명시적 표현 요청을 우선 반영하되, 데이터에 없는 정보나 잘못된 집계를 허용하지 않는다.
표현 요청이 없으면 LLM이 질문과 Knowledge의 힌트를 참고해 선택한다.

### 3.1 Knowledge — 집계 기준과 표현 힌트

이미 구현된 필드를 사용한다.

- `catalog.aggregation_rules`: 원본 행의 의미, 합산 범위, 조인 중복 주의사항
- `kpi.aggregation_rules`, `recipe_refs`: 지표 계산 기준과 집계 레시피 연결
- `recipes.output_grain`, `output_columns`: 레시피 출력의 행 단위와 컬럼 의미
- `recipes.visualization_hints`: 비교·추이에 적합한 표현, 수량·비율 분리 등의 힌트

`visualization_hints`는 권장사항이며, 컬럼 이름이 일치하면 특정 차트를 강제하는 규칙이 아니다.
별도의 `charts:`, `ChartRule`, `when.has_columns` 매칭 계층은 추가하지 않는다.
구체적인 집계 가이드와 SQL은 Knowledge에서 관리하고 이 문서나 Skill에 복제하지 않는다.

### 3.2 LLM — 조회 의도를 명세로 연결

LLM은 SQL을 만들 때부터 차트에 필요한 차원을 고려한다.
실행 후에는 실제 반환 컬럼·타입·샘플과 질문을 확인하고 `prepare_visualization`을 호출한다.
별도 LLM을 추가로 호출하는 구조가 아니라 현재 에이전트가 새 tool을 사용하는 구조다.

예: 연월·라인별 실적이 집계된 결과에 대한 tool 입력.

```json
{
  "result_id": "a30f90f8da934a35a931ba694e130a65",
  "kind": "line",
  "x": "work_month",
  "y": ["actual"],
  "group_by": "line_cd"
}
```

v2 최초 지원은 `kind: bar | line`이다.
`x`는 실제 결과 컬럼, `y`는 하나 이상의 수치 컬럼,
`group_by`는 선택적 시리즈 분리 컬럼이다.
그룹이 없으면 생략한다. 같은 결과에서 계획·실적 비교와 달성률 추이를 별도 명세로 등록할 수 있다.

LLM은 데이터 값 배열, SQL, HTML, JavaScript를 이 tool에 전달하지 않는다.
집계·쿼리 실행은 `execute_sql`, 표현 요청은 `prepare_visualization`이 담당한다.

### 3.3 서버 — 검증하고 명세 등록

`prepare_visualization`은 백엔드 서비스에서 다음을 확인한다.

- 요청 스키마와 지원 차트 종류, 결과의 존재·만료·접근 범위
- `x`, `y`, `group_by` 컬럼 존재 및 중복·충돌 없는 연결
- 수치 데이터의 유효성, 선 차트 시간축의 해석 가능 여부
- `x` 또는 `x + group_by` 조합의 유일성
- 빈 결과, NULL, 항목·시리즈 수, 원본 조회 결과의 잘림 여부

검증 후 렌더링에 필요한 정렬·시리즈 분리만 수행한다.
그룹별 중복을 임의 합산하거나 마지막 값으로 덮어쓰지 않는다.
NULL 수치는 0으로 채우지 않으며, 결측을 유지한다.
코드와 이름이 함께 있으면 코드는 그룹 식별자로 유지하고 이름은 표시 라벨로 사용한다.
시리즈 내부 키는 표시 이름과 분리해 같은 이름이나 컬럼명 충돌로 값이 사라지지 않게 한다.

날짜·월은 해석한 시간 순서로 정렬한다. 선 차트에 상위 N개 규칙을 적용하지 않는다.
최초 버전은 표시 한도를 초과하면 범위 축소·SQL 재조회를 요청하며,
자동 집계·다운샘플링·조용한 잘라내기는 하지 않는다. 상위 N개가 질문의 목적이면 SQL에서 명시한다.
이미 잘린 SQL 결과는 그 범위를 도구 결과와 화면에 표시한다.

서버가 구조를 검증했다고 업무 의미까지 보장되는 것은 아니다.
현재 role은 휴리스틱이고 단위·컬럼 계보도 완전히 확보되어 있지 않다.
수량과 비율의 혼합 등 의미 판단은 Knowledge와 LLM이 담당하며,
서버가 확인 가능한 메타데이터가 있는 경우에만 추가 검증한다.
알 수 없는 단위나 원천을 확인된 사실로 기록하지 않는다.

성공하면 서버가 정규화한 명세를 등록하고 다음처럼 반환한다.

```json
{
  "status": "ok",
  "visualization_id": "b8c19235da17461ab3e8ec82a942f017"
}
```

경고가 있으면 성공 응답에도 포함해 LLM이 실제 표시 범위를 알고 설명할 수 있게 한다.
이 시점에는 HTML을 만들지 않는다. 저장 대상은 결과 참조와 검증된 표현 명세다.

### 3.4 실패·생략 처리

- 잘못된 컬럼·명세: 도구 오류를 LLM에 반환해 명세 수정
- 중복 그룹·불충분한 차원: 추가 집계 또는 원천 데이터 재조회
- 빈 결과·표시 불가: 이유를 설명하고 표 또는 텍스트로 응답
- 차트가 불필요하거나 사용자가 표만 요청: 차트 생략

도구 오류에는 기계적으로 구분할 오류 코드와 LLM이 수정할 수 있는 설명을 제공한다.
보정은 최대 2회로 제한하고, 실패가 계속되면 차트를 약속하거나 잘못된 마커를 출력하지 않는다.
만료 결과는 기존 시각화로 복구하지 않으며 필요한 경우 새 조회·등록을 거친다.

LLM이 tool을 호출하지 않았거나 마커를 생략하면 v2 차트도 표시하지 않는다.
`infer_chart` 또는 답변 후처리로 차트를 자동 첨부하는 폴백은 두지 않는다.

## 4. 최종 답변 참조와 프론트 렌더링

### 4.1 시각화 저장과 조회

두 종류의 데이터를 구분한다.

- **Result Store의 parquet:** DB·시뮬레이션이 반환한 실제 데이터
- **서버의 시각화 메타데이터:** `visualization_id`, `result_id`, 검증된 명세,
  명세 버전, 생성·만료 시각, 접근 범위와 표시 경고

시각화 메타데이터는 서버 재시작 후에도 조회할 수 있게 저장한다.
최초 버전에서는 원본 parquet과 별도로 수치 배열이나 HTML을 중복 저장하지 않는다.
생성한 명세는 변경하지 않고, 다른 표현은 새 ID로 등록한다.

시각화의 수명은 원본 결과보다 길지 않게 한다. 원본 만료·삭제 시 관련 명세도 정리한다.
등록과 조회 모두 원본의 접근 권한·유효성을 확인하며, 임의 ID나 대화 ID만으로 접근을 허용하지 않는다.
현재 결과의 대화 소속 연결이 미완성인 부분은 API 공개 전에 보완해야 한다.
조회 중 원본이 삭제된 경우도 만료·사용 불가 상태로 처리하고 자동 SQL 재실행은 하지 않는다.

```text
GET /api/visualizations/{visualization_id}
  → 검증된 렌더링용 ChartSpec과 표시 메타데이터
```

조회 API는 저장된 명세를 사용한다. URL 쿼리로 새 축·집계 방법을 지정하지 않는다.
기존에 제안했던 `GET /api/results/{result_id}/chart?type=...&x=...&y=...` 집계 API는 폐기한다.

렌더링용 `ChartSpec`은 기존 `type`, `x`, `series`, `categories`, `data`를 바탕으로 한다.
tool 입력의 `kind`는 서버가 렌더링용 `type`으로 변환한다.
제목·축 라벨·단위·경고 등 추가 필드는 백엔드·프론트 공통 계약으로 정의한다.
명세 검증과 데이터 구성은 서비스 계층에 두며, API는 조회·응답을 담당한다.

### 4.2 마커는 검증된 시각화 ID만 참조

LLM은 tool이 성공했을 때 반환된 ID를 최종 답변의 원하는 위치에 삽입한다.

````text
라인별 실적 추이는 다음과 같습니다.

```chart
{"visualization_id": "b8c19235da17461ab3e8ec82a942f017"}
```
````

마커에는 데이터나 축 명세를 넣지 않는다.
tool은 검증·등록·오류 피드백을, 마커는 최종 답변 내 배치를 담당한다.
ID 전사 오류도 서버 조회에서 확인한다.

프론트는 마커를 인식하면 API로 명세와 데이터를 조회하고
기존 Recharts 기반 컴포넌트로 브라우저에서 차트를 그린다.
HTML 파일을 미리 생성하거나 LLM이 만든 HTML·JavaScript를 실행하지 않는다.
현재의 assistant-ui·애플리케이션 소유 메시지 상태·SSE 전송 구조를 유지한다.

### 4.3 로딩·실패·스트리밍

- 스트리밍 중 미완성 마커는 로딩 상태로 처리한다.
- 완성된 마커의 스키마와 ID가 유효할 때만 조회한다. JSON 파싱 성공만으로 요청하지 않는다.
- 응답 완료·취소 후에도 마커가 잘못되어 있으면 오류 상태로 전환한다. 무한 스켈레톤을 남기지 않는다.
- 조회 실패·만료는 짧은 설명과 원본 표 확인 안내로 표시한다.
  원본도 만료되었다면 새 조회가 필요하다고 알린다.
- 같은 ID의 중복 요청을 합치고, 표시 대상 변경·언마운트 시 진행 중 요청을 취소한다.
- 네트워크 조회 재시도와 LLM의 명세 보정을 구분한다.
  프론트의 조회 오류만으로 LLM이 자동 재실행된다고 가정하지 않는다.

### 4.4 에이전트 절차 연동

`sql-analysis`와 `simulation` Skill에 다음 절차를 추가한다.

> 비교·추이가 유용하거나 사용자가 차트를 요청하면, 집계 가이드와 실제 결과를 확인한 뒤
> prepare_visualization을 호출한다. 오류는 제한된 횟수 내에서 보정하고,
> 성공한 경우에만 반환된 visualization_id를 최종 답변의 chart 마커에 사용한다.
> 지원하지 않는 표현이나 데이터가 부족한 경우 사유를 설명한다.

이 문구는 v2 tool 등록과 함께 적용한다. 현재 등록되지 않은 tool을 먼저 안내하지 않는다.
Skill에는 실제 테이블·컬럼을 복제하지 않고 절차만 둔다.
표형 시뮬레이션 결과도 같은 검증 경로를 사용하며, SQL로 재조회할 수 없는 결과는
지원되는 시뮬레이션 조건 변경 또는 표 표시로 처리한다.

## 5. 구현 순서와 완료 기준

### 구현 순서

1. **결과 계약 보완:** 소량·대용량 컬럼 메타데이터 일관성, 결과 잘림 표시, 결과 접근 범위 연결
2. **시각화 서비스:** 입력 스키마, 저장 데이터 검증, 렌더링용 데이터 구성, 명세 저장·만료 정리
3. **tool 등록:** `prepare_visualization`과 성공·오류 계약, SDK 등록·fake runner·프롬프트 정합성 테스트
4. **조회 API·프론트:** `GET /api/visualizations/{id}`, ID 마커 렌더, 다중 시리즈·라벨·로딩·오류 처리
5. **에이전트 절차:** Knowledge → 집계 → 시각화 요청 → 검증된 마커의 흐름 연결
6. **v1 정리:** 전체 흐름 검증 후 자동 chart 첨부와 도구 카드의 중복 차트 제거

### 완료 기준

- 서로 다른 별칭·집계 단위의 SQL 결과에서도 실제 컬럼을 선택해 최종 답변에 차트가 표시된다.
- 같은 결과에서 계획·실적 비교와 달성률 추이를 각각 등록하고, 원본 수치를 그대로 사용한다.
- 중복 날짜·그룹은 조용히 합산·덮어쓰지 않고 보정 가능한 오류가 된다.
- NULL, 분모 0에서 나온 결측 비율, 시간 정렬, 동명 그룹, 다중 시리즈를 올바르게 표시한다.
- 표시 한도와 SQL 결과 잘림을 구분하며 시계열을 임의로 잘라 추이를 왜곡하지 않는다.
- 잘못된 마커, 스트리밍 취소, 조회 실패, 원본 만료·삭제·접근 불가가 무한 로딩 없이 처리된다.
- tool 미호출·보정 실패 시 표·텍스트 응답이 유지되고 자동 차트가 추가되지 않는다.
- 재시작 후 유효한 명세를 조회할 수 있고 만료된 원본의 시각화는 조회되지 않는다.

아래 실행 계획은 이 문서의 `prepare_visualization`·ID 전용 마커·조회 API 흐름에 맞춰 갱신했다.
구현 중 계약이 달라지면 이 문서를 먼저 고치고 두 계획을 함께 맞춘다.

## 6. 범위와 구현 전 확정할 사항

- **최초 지원:** bar/line. 표는 기존 결과 표시를 사용한다.
  간트는 실제 작업 식별자·시작·종료·자원 데이터가 확보되면 별도 명세와 렌더러로 확장한다.
  현재 일별 계획·실적 수량에서 작업 구간을 추정하지 않는다. pie도 최초 범위 밖이다.
- **표시 한도:** bar/line별 포인트·시리즈 상한과 너무 큰 결과의 사용자 안내를
  공통 API 계약에서 확정한다. 자동 다운샘플링은 이후 별도 설계한다.
- **의미 메타데이터:** 동적 SQL 결과의 단위·컬럼 계보를 신뢰할 수 있게 연결할 방법은 후속 과제다.
  현재 레시피 힌트나 dtype·role 추정을 서버 검증 완료로 간주하지 않는다.
- **명세 저장 구현:** 영속 저장 위치·버전 호환·원본 삭제 시 정리 방식은
  Result Store 수명주기와 함께 실행 계획에서 확정한다.
- **품질 평가:** 대표 질문별 올바른 컬럼 선택, 차트 생략·남발, 보정 성공 여부와
  추가 tool 호출 지연을 확인한다. 스키마 검증만으로 LLM의 판단 품질이 보장되지는 않는다.
